## ۱. زمینه
فریمورک باید بتواند طیف وسیعی از کاربردها را پوشش دهد: از یک وبلاگ شخصی (ساده)
تا یک ERP سازمانی (بسیار پیچیده). هیچ معماری واحدی برای همهٔ این طیف بهینه نیست:

- **MVC کلاسیک**: برای پروژهٔ کوچک خوب است اما در دامنهٔ بزرگ به God Controller می‌رسد.
- **ماژولار مونولیت**: مرز دامنهٔ خوب دارد اما برای UI تودرتو کافی نیست.
- **میکروسرویس از روز اول**: پیچیدگی عملیاتی سنگین برای اکثر پروژه‌ها.
- **Event-Driven**: coupling را کم می‌کند اما به‌تنهایی ساختار نمی‌دهد.

نیروهای متضاد: سادگی در برابر انعطاف، استقرار آسان در برابر مقیاس‌پذیری،
سرعت توسعه در برابر تمیزی معماری.

## ۲. تصمیم
تَوان یک **معماری ترکیبی لایه‌ای** اتخاذ می‌کند که پنج الگو را در بر می‌گیرد،
هرکدام مسئول یک مسئلهٔ متفاوت:

| الگو | مسئله | لایه |
|---|---|---|
| Layered | جداسازی مسئولیت فنی | همه |
| HMVC | بازاستفادهٔ UI و کنترل جریان | Presentation |
| Modular Monolith | مرز دامنه + استقرار ساده | ماژول‌ها |
| Event-Driven | کاهش coupling بین دامنه‌ها | بین ماژول |
| Hexagonal | جداسازی دامنه از فناوری | Domain/Infra |

**حالت پیش‌فرض: Modular Monolith.** میکروسرویس یک گزینهٔ استقرار است، نه بازنویسی.

## ۳. گزینه‌های بررسی‌شده
| گزینه | مزایا | معایب |
|---|---|---|
| MVC ساده | سادگی، سرعت اولیه | God Controller، مرز ضعیف |
| فقط ماژولار | مرز خوب | UI تودرتو سخت |
| میکروسرویس از ابتدا | مقیاس مستقل | پیچیدگی عملیاتی، Distributed Monolith |
| **ترکیبی لایه‌ای (انتخابی)** | انعطاف، پوشش کامل، استخراج تدریجی | نیازمند انضباط، یادگیری بیشتر |

## ۴. دلایل انتخاب
- **اصل P3 (کمینه‌دانی هسته)**: هسته فقط اجرا؛ الگوها در لایه‌های بالاتر.
- **اصل P4 (مرزهای روشن)**: ماژولار + HMVC مرزهای سخت می‌دهند.
- **اصل P5 (رویداد به‌جای فراخوانی)**: ED coupling را کم می‌کند.
- **اهداف G6/G7**: انعطاف معماری + مقیاس‌پذیری دامنه.
- کاربر می‌تواند `app.architecture` را از `mvc` تا `hexagonal` انتخاب کند (DOC-021 §5).

## ۵. پیامدها
### مثبت
- پوشش همهٔ سطوح پیچیدگی
- مسیر رشد تدریجی (mvc → modular → hexagonal → microservice)
- مرزهای روشن برای تست و نگهداشت
- امکان استخراج سرویس بدون بازنویسی

### منفی / هزینه
- منحنی یادگیری بالاتر برای تازه‌واردها
- نیاز به انضباط معماری (arch:check)
- مستندات بیشتر

### ریسک‌ها
- نقض مرزها توسط توسعه‌دهندگان → mitigation: `tvn arch:check` اجباری در CI
- پیچیدگی بیش از حد برای پروژهٔ کوچک → mitigation: `mvc` mode

## ۶. انطباق
- ساختار پوشه (DOC-080) باید لایه‌ها را منعکس کند.
- قوانین Arch (DOC-021 §7) در CI اجرا شوند.
- Scaffold بر اساس `app.architecture` کد تولید کند.
