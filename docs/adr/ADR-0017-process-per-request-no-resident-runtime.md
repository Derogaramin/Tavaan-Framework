# ADR-0017 — مدل اجرا: Process-per-request (بدون runtime مقیم اجباری)

| متادیتا | مقدار |
|---|---|
| شماره | ADR-0017 |
| وضعیت | **Accepted** |
| تاریخ | 2026-10-26 |
| سطح اثر | Global (Deployment/Performance) |
| مرتبط | ADR-0004 (صفر‌وابستگی)، ADR-0014 (no-vendor-runtime)، DOC-112 (اهداف کارایی)، DOC-130 §7، گزارش `framework-critique-1.0.md` §1.3 |

## ۱. زمینه

نقد مستقل 1.0 (`docs/reports/framework-critique-1.0.md`) یک **سقف ساختاری
کارایی** را برجسته کرد: هر درخواست وب = یک بوت کامل فریمورک
(~۵–۶٫۵ms warm با opcache، اندازه‌گیری‌شده). هدف DOC-130 «RPS ≥ ۳۰۰۰
(Swoole)» مستلزم یک **runtime مقیم** (Swoole/OpenSwoole/RoadRunner/FrankenPHP)
است که فرایند را زنده نگه دارد و بوت را حذف کند — اما همهٔ این‌ها **افزونهٔ
باینری یا باینری خارجی** هستند و با سیاست صفر‌وابستگی (ADR-0004/0014: بدون
هیچ پکیج/افزونهٔ خارجی در زمان اجرا) در تضاد‌اند.

بدون runtime مقیم، سقف RPS per-core ≈ `1000ms / (boot + handler)` ≈ ۱۰۰–۱۵۰
است (نه ۳۰۰۰). این یک واقعیت معماری است، نه باگ.

## ۲. تصمیم

**process-per-request مدل پیش‌فرض و پشتیبانی‌شدهٔ استقرار باقی می‌ماند**
(php-fpm/CLI-server). مقابله با سقف RPS از سه راه، **بدون نقض صفر‌وابستگی**:

1. **بهینه‌سازی بوتِ خودِ مدل per-request** (مسیر اصلی):
   - `opcache` + **`opcache.preload`** برای پیش‌بارگذاری کلاس‌های پرکاربرد
   - `tvn optimize` (کش config + classmap authoritative + route cache)
   - بوت lazy: providerها تنها در صورت مصرف، سرویس می‌سازند (وضع موجود)
   - هدف بازنگری‌شده: بوت warm ≤ ۵ms با preload (در برابر ۸ms مستند M1)
2. **scale افقی** به‌جای یک ابرفرایند: فریمورک stateless-per-request است ⇒
   افزودن fpm worker / نود پشت LB تقریباً خطی مقیاس می‌شود (تا سقف CPU).
   پریمیتیوهای لازم (cache با ۶ درایور شامل redis، queue، session
   چنددرایور، tenancy) موجود است.
3. **لایهٔ اختیاری runtime مقیم** به‌عنوان **پل استقرار** (نه هسته):
   یک `tavaan-runtime-adapter` **جدا و opt-in** (پلاگین امضاشده یا پکیج
   استقرار) که در صورت حضور Swoole/FrankenPHP، بوت را یک‌بار انجام داده و
   Container را بین درخواست‌ها بازیافت می‌کند. هسته **هرگز** به آن وابسته
   نمی‌شود؛ نبودش هیچ قابلیتی را نمی‌گیرد (فقط RPS-per-core پایین‌تر).

**هدف DOC-130 «RPS ≥ ۳۰۰۰» از معیار انتشار 1.0 حذف و به 1.x موکول می‌شود**
(مشروط به تحویل لایهٔ اختیاری بند ۳). معیار 1.0 برای کارایی: بوت warm ≤ ۸ms،
سربار per-request ≤ ۳ms، route match ≤ ۵µs — که **همه پاس شده‌اند** (نقد §1).

## ۴. پیامدها

- DOC-130 §7 و DOC-120 §6: هدف RPS≥۳۰۰۰ **به تعویق (1.x)** — با برچسب
  «نیازمند adapter اختیاری».
- راهنمای استقرار (DOC-133): تنظیمات nginx+php-fpm، `opcache.preload`،
  تعداد worker بر پایهٔ هسته، و note صریح دربارهٔ سقف per-core.
- backlog: تیکت «runtime adapter اختیاری (FrankenPHP/Swoole)» در 1.x.
- bench: افزودن سناریوی «با preload» برای ثبت بهبود بوت.

## ۵. اعتبارسنجی

- اندازه‌گیری نقد §1: بوت warm ۴٫۹–۶٫۵ms (هدف ≤۸ms پاس)، per-request
  overhead ۰٫۱۳ms (هدف ≤۳ms پاس)، route match ۲–۳µs (هدف ≤۵µs پاس).
- burst ۱۰۰۰@۳۰۰ و flood ۲۰۰۰@۲۰۰: صفر 5xx اپلیکیشن (پایداری مدل
  per-request زیر بار) — `tools/scripts/load-test.php`.
- اثبات scale افقی: افزودن worker تا سقف هسته RPS را بالا برد؛ فراتر از
  هسته، اشباع CPU (نه قفل نرم‌افزاری) — یعنی مقیاس‌پذیری تا سقف سخت‌افزار.
