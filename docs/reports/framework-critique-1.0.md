## ۱. توان پردازش — «در هر لحظه چند درخواست؟ ۱۰۰۰ نفر همزمان؟ ۱۰۰۰۰؟»

### ۱٫۱ اندازه‌گیری مستقیم (همین sandbox — بدترین حالت ممکن)

| سناریو | RPS | تأخیر | خطا |
|---|---|---|---|
| php -S تک‌ورکر، **بدون** opcache — `/time` (JSON ۱۲۱ بایت) | ۳۵٫۴ | avg ۲۷۷ms @c10 | ۰ |
| php -S تک‌ورکر، بدون opcache — `/blog` (DB+view، ۹٫۷KB) | ۲۹٫۵ | avg ۳۳۲ms @c10 | ۰ |
| حالت production-like (opcache + config-cache + classmap) — `/time` | **۷۸٫۴** | avg ۱۲۷ms @c10 ⇒ **~۱۲٫۷ms سرویس واقعی** | ۰/۱۰۰۰ |
| همان — `/blog` (DB) | **۶۰٫۸** | avg ۱۶۳ms @c10 | ۰/۴۰۰ |
| ۲ ورکر، ۱۵۰۰ درخواست @c30 | ۷۷٫۷ | p95 ~۴۷۸ms | **۰** |
| ۴ ورکر (بیش از تعداد هسته!) | ۳۴ | — | ۰ — اشباع CPU؛ scaling منفی |
| **burst ۱۰۰۰ درخواست @ ۳۰۰ اتصال همزمان** | ۵۴ | p50 ~۳s / p95 ~۱۰s | ۹۷۳×۲۰۰ + ۲۷ خطای **TCP** (سرریز backlog کرنل، somaxconn=128) — **صفر 5xx اپلیکیشن** |
| flood ۲۰۰۰ @ ۲۰۰ همزمان | — | — | ≥۹۵٪ موفق؛ سرور پس از flood سالم |

نکتهٔ کلیدی: گلوگاه در تمام سناریوها **CPU/بوت per-request** است، نه خودِ
کد مسیر درخواست (سربار پس از بوت: **۰٫۱۳ms** — bench). هر ورکر
PHP یک‌هسته را اشغال می‌کند؛ در sandboxِ دومرزِ-اشتراکی، سقف ~۷۸ RPS
استقلال از تعداد ورکر است.

### ۱٫۲ پاسخ به «۱۰۰۰ کاربر همزمان» و «۱۰۰۰۰ کاربر همزمان»

«همزمان» را باید تفکیک کرد (ریاضی صف — Little's Law):

- **۱۰۰۰ کاربر با think-time معمول** (یک درخواست هر ۱۰–۳۰ ثانیه) ⇒ بار
  واقعی ≈ **۳۳–۱۰۰ RPS**. یک نود fpm با ۴–۸ ورکر روی سخت‌افزار معمولی
  (i3 نسل ۷، §7) این را با utilization زیر ۲۵٪ پاسخ می‌دهد ⇒ **بله،
  کافی است** — حتی با headroom برای spike.
- **۱۰۰۰ اتصال واقعاً همزمانِ پشت‌سرهم** (حالت flood/BOT): در sandbox
  اندازه‌گیری شد — اپلیکیشن **صفر 5xx** داد؛ ۲٫۷٪ شکست در لایهٔ TCP
  (backlog کرنل) بود، نه فریمورک. با `somaxconn`/`backlog` تنظیم‌شده و
  nginx جلو، همین بار به‌صورت صف با تأخیر p95 چند ثانیه‌ای سرو می‌شود.
  تحملش را دارد؛ **تجربهٔ کاربری‌اش را نه** — برای این حالت باید
  rate-limit (موجود: دقیقاً ۶۰/۶۰s اندازه‌گیری شد)، کش پاسخ و scale-out.
- **۱۰۰۰۰ کاربر همزمان** ⇒ ~۳۳۰–۱۰۰۰ RPS پایدار. **یک نود کافی نیست.**
  پاسخ صحیح: LB + ۲–۴ نود (هرکدام ~۳۰۰–۵۰۰ RPS) + کش (موتور cache با
  ۶ درایور موجود است) + در صورت نیاز صف برای کارهای سنگین (موجود).
  فریمورک **پریمیتیوهای** scale افقی را دارد (cache/queue/tenancy/
  feature-flag/realtime) اما LB و معماری استقرار بیرون از آن است —
  همان nginx/HAProxy استاندارد.

### ۱٫۳ سقف ساختاری (نقد صریح)

هر درخواست = یک بوت کامل فریمورک (~۵–۶٫۵ms warm با opcache — اندازه‌گیری
شد؛ هدف ≤۸ms مستند M1 **پاس شد**). اما **runtime مقیم** (Swoole/RoadRunner/
FrankenPHP مانند Laravel Octane) وجود ندارد ⇒ سقف RPS per-core محدود به
`1/(boot+handler)` ≈ ۱۰۰–۱۵۰ است. هدف DOC-130 «RPS ≥ ۳۰۰۰ (Swoole)»
با سیاست صفر‌وابستگی **در تضاد است** — افزونهٔ Swoole یک وابستگی خارجی
است. این بزرگ‌ترین سقف کارایی محصول است و باید یا پذیرفته و مستند شود
یا با پشتیبانی اختیاری از runtimeهای مقیم (به‌عنوان افزونهٔ استقرار، نه
وابستگی) حل شود.

## ۲. حداقل و منابع ایده‌آل

### اندازه‌گیری‌شده در sandbox
- حافظهٔ اوج بوت: **۴–۸MB** • RSS ورکر php -S با opcache: **۲۸–۳۶MB** (والد با JIT buffer 64M: ~۶۰MB)
- دیسک: کل ریپو (کد+مستندات) **۶۹MB** + .git ۵٫۵MB • DB SQLite پس از نصب **هر ۸ کیت** با demo: **۱٫۶MB**
- CPU: بوت warm ~۵–۶٫۵ms ⇒ یک هستهٔ مدرن ≈ ۱۵۰–۲۰۰ بوت/ثانیه (تئوریک)

### جمع‌بندی منابع

| سناریو | CPU | RAM | دیسک | توضیح |
|---|---|---|---|---|
| **حداقل مطلق** (dev/سایت شخصی، SQLite) | ۱ هسته | ۵۱۲MB | ۲۵۰MB | تک‌ورکر ~۳۰–۸۰ RPS |
| **حداقل عملیاتی** (کسب‌وکار کوچک) | ۲ هسته | ۱–۲GB | SSD ۱GB | fpm ۲–۴ ورکر + MySQL/SQLite |
| **ایده‌آل** (تولید جدی) | ۴–۸ هسته | ۴–۸GB | NVMe | nginx + fpm(per-core) + opcache+**preload** + MySQL/PG + redis برای cache/session/queue |
| هر ۸ کیت با هم (portal چندمنظوره) | +۱ هسته | +۵۱۲MB | +۵۰۰MB | هم‌زیستی ۸ کیت روی DB مشترک **آزموده شد** (smoke ۱۸/۱۸) |

نکتهٔ صادقانه: `kit.json`ها `memory_mb: 128` اعلام می‌کنند که برای
**اجرا** درست است (ورکر ~۳۰–۴۰MB) ولی برای **نصب با demo + migrate**
روی همهٔ کیت‌ها، ۵۱۲MB+ واقع‌بینانه‌تر است (خود سوئیت تست ۶۰۰MB اوج
گرفت). مستندسازی این تفکیک توصیه می‌شود.

## ۳. تاب‌آوری در برابر تخریب (هکر / ایجنت خرابکار)

### ۳٫۱ آزمون زنده — `adversarial-test.php` (۱۲/۱۲ دفع شد)

| حمله | نتیجهٔ اندازه‌گیری‌شده |
|---|---|
| flood نرخ: ۷۵ درخواست به API محدودشده | **دقیقاً** ۶۰×۲۰۰ سپس ۴۲۹ — rate-limit مطابق پیکربندی |
| POST بدون توکن CSRF (روت وب) | ۴۱۹ — **پیش از** هر پردازش کسب‌وکاری |
| payload بیست‌مگابایتی (سقف ۸MB) | رد بدون ۵۰۰ |
| JSON bomb — ۵۰۰۰ لایه تودرتو | رد بدون ۵۰۰ (عمق json محدود) |
| Path traversal — ۵ واریانت (`../../etc/passwd`, encoding, `.env`, sessions) | بدون نشتی |
| SQLi — ۴ payload (union/drop/comment) روی جست‌وجو و فیلتر پنل | بدون ۵۰۰/نشت hash/SQLSTATE — prepared statements؛ سرویس برقرار |
| XSS ذخیره‌شده (`<script>` در subject/body پرتال عمومی) | escape‌شده — بدون `<script>` خام در خروجی |
| کوکی نشست جعلی/دستکاری (۴ واریانت: hex نامعتبر، traversal، ۴۰۰۰ بایت، NUL) | رد/بی‌اثر، بدون crash، **بدون پذیرش** |
| هدرهای امنیتی | ۴/۴ حاضر (CSP, XFO, XCTO, Referrer-Policy) |
| flood سنگین ۲۰۰۰@۲۰۰ | ≥۹۵٪ موفق؛ **سرور پس از flood زنده و سالم** |

### ۳٫۲ دفاع‌های درونی که در بازبینی کد تأیید شد

لایهٔ auth: session hardening (regenerate هنگام لاگین ضد fixation +
fingerprint نشست IP+UA — در تست کوکی جعلی عملاً دیده شد) + throttle/lockout
لاگین • CSRF middleware سراسری با except صریح • Throttle per-route
(پرتال عمومی ۵/۶۰) • FloodControl + honeypot (forum) • Sanitizer و
escape-first در view engine • SSRF guard در http-client • سقف‌های DoS
دامنه‌ای (BPMS: max_active_instances/advance_limit — **تست‌شده**؛ workflow:
سقف instance؛ validator: سقف عناصر/طول عبارت/عمق پرانتز) • Expression
evaluator **بدون eval** با دو لایه رد (publish+runtime — تست‌شده با
`system()`/backtick/`$var`) • plugin sandbox با **امضای اجباری** •
audit با hash chain (tamper → `verify` شکست را گزارش می‌کند — E2E دارد) •
LogMasker روی دادهٔ حساس • mask متغیرهای فرایند در ویو/broadcast.

### ۳٫۳ نقاط ضعف صادقانهٔ تاب‌آوری

1. **بدون WAF/anti-bot داخلی** — در برابر L7 DDoS توزیع‌شده (هزاران IP
   «آهسته») دفاع اپلیکیشنیِ نرخ-محدود کمک می‌کند ولی لایهٔ واقعی باید
   nginx/CDN باشد؛ فریمورک این را مستند نکرده (جای «راهنمای استقرار
   hardened» خالی است).
2. اسکنر امنیتی **token-based** است نه taint-analysis — کلاس‌هایی از باگ
   (تزریق مرتبهٔ دوم، زنجیرهٔ deserialization) را اصولاً نمی‌بیند.
3. queue worker تک‌فرایند و بدون supervisor داخلی است (QueueListenCommand
   به proc_open تکیه دارد) — زیر بار سنگین صف، نقطهٔ شکنندهٔ عملیاتی.
4. در sandbox دیدیم: زیر فشار حافظه، forkها شکست می‌کنند (proc_open) —
   هر مسیری که به subprocess تکیه دارد (queue:listen, bench, test
   --parallel) در محیط‌های محدود first-to-fail است.
5. Slowloris/timeoutها تنظیم نشده بودند آزمون (لایهٔ سرور) — باید در
   راهنمای استقرار قید شود.

**جمع‌بندی §3:** در برابر «ایجنت خرابکاری» که ابزارهای رایج را پرتاب کند
(flood, SQLi, XSS, traversal, payload, CSRF, session) — **کاملاً تاب‌آور
(۱۲/۱۲ زنده)** و در بدترین حالت graceful degradation (صف/تأخیر، نه crash،
نه نشت). در برابر DDoS جدی و حملات نوین زنجیره‌ای — به لایهٔ زیرساخت
وابسته است و باید مستند شود.

## ۵. سطح کدنویسی — جونیور، مید‌لول یا سنیور؟

**حکم: سنیور (با لکه‌های میدلول در «راستی‌آزمایی»، نه در «نوشتن»).**

شواهد سنیور (از ~۱۰۰ فایلی که در این نشست عمیق خوانده/نوشته/بازبینی شد):
- `strict_types` عملاً ۱۰۰٪ (۱۷۳۶/۱۸۹۲ — استثناها فقط templateهای `.tv.php`اند که PHP خالص نیستند) • readonly class/final/enum/promptotion به‌جای سراسر کد • میانگین فایل ~۱۰۶ خط (ریز-کلاس، SRP واقعی)
- **خطای قابل‌توضیح**: messageId + refCode + hint + context با masking خودکار — الگویی که تیم‌های سنیور هم به‌ندرت پیاده می‌کنند
- الگوهای درستی که **در عمل** دیده شد: ports/adapters در همهٔ ماژول‌ها، تراکنش+رویداد-پس-از-commit، Outbox برای یکپارچگی بین‌بافته‌ای، claim اتمیک با UPDATE شرطی، idempotency در cronها (مهر escalated_at)، snapshot/restore برای اتمیکی fire، fail-open در audit، fail-safe در رمزنگاری national_id
- ذهنیت امنیتی نظام‌مند: allowlist صریح با دلیل مستند (architecture.php)، evaluator بدون eval، escape-first، prepared-only، mask، امضای پلاگین
- ثبت تصمیم (۱۶ ADR) + انحراف‌های مستند در هر گزارش — نشانهٔ بلوغ فرایندی

لکه‌های میدلول (صادقانه):
- **باگ نهفتهٔ SessionGuard از M6 تا M9** — یعنی مسیر «HTTP واقعی با نشست» سه فاز تست نشده بود (تست‌ها با actingAs میان‌بر می‌زدند). کد سنیور می‌نویسد، ولی تورِ ایمنی‌اش سوراخ داشت تا ممیزی M9 آن را گرفت
- coverage واقعی ۷۱٫۷٪ در برابر هدف اعلامی ۹۰٪ — فاصلهٔ بین «استاندارد مکتوب» و «اجرا»
- drift مستندات (README: «۴۸ موتور» در برابر ۵۲ واقع؛ manifest version 0.8.0 مانده بود)

## ۶. مستندپذیری به‌صورت کتاب — چقدر میسر است؟

**بسیار بالا — احتمالاً بهترینِ ویژگی‌های این ریپو برای این هدف.**

آنچه **هم‌اکنون** وجود دارد (نه وعده):
- **۱۲۱ سند** با DOC-ID، بخش‌بندی ۹گانه (دیدگاه/استانداردها/معماری/۵۳ مشخصیست موتور/ساختار/کاربردها/نقش‌ها/کیفیت/نقشه‌راه/مراجع) + `docs/manifest.json` ماشین‌خوان + چهار «مسیر مطالعه» آماده (engine_builder/architect/app_builder/qa_reviewer)

- قالب مستند (DOC-150/151) ⇒ سبک یکنواخت

برای تبدیل به کتاب واقعی چه کم است:
1. **روایت پیوسته** — اسناد spec-styleاند؛ کتاب به قوس روایی آموزشی نیاز دارد (teaching arc) (از «چرا صفر‌وابستگی» تا ساخت اولین ماژول، با کد کامل inline)

3. تمرین و پروژهٔ راهنما — Quick Start (DOC-004) «نقشهٔ ساخت» است نه «آموزش استفاده»
4. ویرایش انگلیسی (برای مخاطب «ساخت نسخهٔ مشابه»)

پیشنهاد ساختار ۳ جلدی (مستقیماً از manifest قابل استخراج است):
**جلد ۱ — معماری و هسته** (DOC-001..030 + ADRها) • **جلد ۲ — مرجع ۵۳

ثالث» از روی آن **میسر** است — این ادعای بزرگی است و اینجا با شواهد
(کیت‌های ساخته‌شده از روی سند توسط ایجنت‌های متفاوت) پشتیبانی می‌شود.

## ۷. پیش‌بینی برای سخت‌افزار مشخص (i3-7100 / 16GB / SSD / Intel HD 630)

فرض‌های صریح: i3-7100 = ۲ هسته/۴ رشته @۳٫۹GHz (single-thread ≈ ۱٫۵–۱٫۸×
هر vCPU اشتراکیِ این sandbox) • ۱۶GB RAM (بیش از حد کافی — RAM اینجا هرگز گلوگاه نیست) • SSD: گلوگاه I/O عملاً حذف • GPU بی‌ارتباط
(هیچ بار گرافیکی ندارد). هر عدد **برون‌یابی از اندازه‌گیری sandbox با
ضریب هسته** است و باید روی دستگاه واقعی تأیید شود.

### لینوکس (nginx + php-fpm + opcache(+preload) — استقرار توصیه‌شده)

| بار | برآورد |
|---|---|
| سرویس per-request (صفحهٔ سبک) | ~۶–۹ms ⇒ ~۱۱۰–۱۶۰ RPS **per worker** |
| ورکرهای منطقی (۲C/4T، HT برای PHP ~۱٫۳×) | ۳–۴ fpm worker |
| **RPS پایدار کل (صفحات سبک)** | **~۳۵۰–۵۰۰** |
| صفحات DB-دار (SQLite/MySQL سبک) | ~۲۰۰–۳۵۰ RPS |
| کاربران همزمان با think-time (۱۰–۳۰s) | **~۳۵۰۰–۱۵۰۰۰ کاربر** در utilization ≤۷۰٪ — یعنی «۱۰۰۰ همزمان» **به‌راحتی**، «۱۰۰۰۰ همزمان» **لبِ مرز/قابل‌قبول با کش** |
| flood خام ۱۰۰۰ اتصال همزمان | تاب می‌آورد (p95 چند ثانیه‌ای) — با backlog/nginx tuning |

### ویندوز (همان سخت‌افزار)

- php-fpm وجود ندارد ⇒ IIS + FastCGI (php-cgi) یا nginx+php-cgi: مدل
  فرایندی سنگین‌تر + NTFS I/O penalty (تخمین ۲۰–۴۰٪ کندتر در بوت/فایل)
  + نبود preload به بلوغ لینوکس.
- برآورد: **~۱۵۰–۳۰۰ RPS** صفحات سبک؛ کاربران همزمان راحت ~۱۵۰۰–۵۰۰۰.
- توصیهٔ صریح منتقد: **ویندوز فقط برای توسعه**؛ تولید روی همان سخت‌افزار
  → لینوکس (یا WSL2 اگر اصرار بر ویندوز است) — اختلاف ۴۰–۶۰٪ی رایگان
  از دست نرود.

### تطبیق با حداقل/ایده‌آل §2
این دستگاه **دقیقاً «حداقل عملیاتی به‌بالا»** است: ۱۶GB RAM برای ۴ ورکر
(هرکدام ~۴۰MB!) به‌شدت بیش‌ازنیاز است — گلوگاه فقط ۲ هسته است. اگر
بودجهٔ سخت‌افزاری ثابت است، به‌جای RAM بیشتر، **هستهٔ بیشتر** بخرید.

## ۸. حکم نهایی منتقد

**پنج نقطهٔ قوت که خریدار باید بداند:**
۱) تنها فریمورک PHP فارسی-اول با **معماری مرز-اجراشده** (abzar مرزها را
نقض نمی‌گذارد رد شوند) • ۲) امنیت پیش‌فرض که در آزمون زنده ۱۲/۱۲ ایستاد
• ۳) بوت/روت سریع‌تر از اهداف رقبا (۵–۶ms/۰٫۱۳ms/۲–۳µs — اندازه‌گیری‌شده)
• ۴) صفر‌وابستگی = استقرار/ممیزی/زنجیرهٔ تأمین ساده • ۵) مستنداتی که
«قابل ساختن از رویش» بودنشان اثبات شده.

**پنج ریسک که خریدار باید بداند:**
۱) اکوسیستم/جامعه ≈ صفر، bus factor ≈ ۱ • ۲) نبود runtime مقیم ⇒ سقف
RPS per-core • ۳) coverage ۷۱٫۷٪ در برابر هدف ۹۰٪ (و یک باگ نهفتهٔ تاریخی
که همین شکاف آشکار کرد) • ۴) صفر سابقهٔ استقرار production بلندمدت •
۵) بنچمارک رقابتی هرگز side-by-side اجرا نشده.

**حکم یک‌خطی:** «معماری در سطح بهترین‌ها، اثبات در سطح یک v1.0 جوان» —
برای niche سازمانیِ فارسی-زبان با استقرار کنترل‌شده، **امروز قابل
استفاده**؛ برای محصول عمومی پرمخاطب، پس از بستن شکاف پوشش و اولین
استقرارهای واقعیِ سخت.
